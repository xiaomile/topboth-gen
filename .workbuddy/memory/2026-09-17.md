## topboth-gen MCP 接入 WorkBuddy（多客户端兼容改造）

**背景**：`G:\github\topboth-gen` 是一个 stdio MCP 服务（Burgeon/Agnes 图片生成），
原先只 documentation了 Trae/Qoder。目标：让 WorkBuddy 也能接入。

**发现的真实根因**：
1. 仓库里没有 `pyproject.toml` / `uv.lock`，README 里的 `uv run mcp_server.py`
   在新机器上直接 `ModuleNotFoundError: httpx`。
2. 代码只写了 mcp SDK **1.x** 的装饰器 API（`@app.list_tools()` / `@app.call_tool()`）。
   mcp **2.x 已删除这两个装饰器**，改用
   `Server(name, on_list_tools=..., on_call_tool=...)`，
   在 2.x 下启动即 `AttributeError: 'Server' object has no attribute 'list_tools'`，
   客户端表现为「连接关闭」。`uv add mcp` 今天装到的就是 2.x。
3. `download_image_sync` 用了未声明的 `requests`（依赖里只有 httpx），URL 图生图会静默失败。

**改动**：
- `mcp_server.py`：按运行时自动适配 1.x / 2.x 两代注册方式；日志统一走 stderr；
  `.env`/输出目录不依赖 cwd；图片入参宽容解析（别名、JSON 字符串、file://、
  `%20`、`/C:/` 等）；路径取不到时明确报错而不是把路径当 base64 透传；
  生成结果落盘并回传 `local_path`；`requests` 换成 `httpx`；新增 `server_status` 自检工具。
- 新增 `pyproject.toml`（含 `[tool.uv] package = false`）、`.env.example`、`.gitignore`、
  `tests/smoke_test.py`（6 项入参/协议检查）。
- `README.md`：补 WorkBuddy 配置（`~/.workbuddy/mcp.json`，必须绝对路径 + `--directory`，
  保存后到连接器页点「信任」）、图生图传图说明、兼容性说明、自测与排障。
- 本机 `~/.workbuddy/mcp.json` 已写入 `topboth-gen` 配置（`MCP_API_KEY` 为占位符，待用户替换）。

**结论（用户问：WorkBuddy 上传的图片能传给 MCP 吗）**：能。客户端把上传图片落成本地文件，
Agent 拿到本地绝对路径传给 `images` 参数即可；也支持 URL / base64 / data URI。

**验证**：`tests/smoke_test.py` 在 mcp 2.2.0 与 mcp 1.30.0 下均 PASS；
用本地假后端跑通「生成 → 落盘 → 返回 local_path + 内联图片」全链路。
（沙箱内无法在 G: 盘创建 `.venv`，`uv sync` 需用户在本机执行一次。）
